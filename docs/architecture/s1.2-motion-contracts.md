# S1.2 Simulator-independent Motion Contracts

**Status:** Implemented baseline on Windows
**Date:** 2026-10-02

## Purpose

These contracts isolate the project from CuRobo, MPlib, RoboTwin/SAPIEN and future physical Panthera APIs.
Third-party objects must be converted at adapter boundaries; they do not cross project subsystem interfaces.

The baseline is intentionally simulator-independent so its semantics can be tested on Windows before the
native-Ubuntu planner/simulator gates.

## Core flow

```text
MotionGoal + PlanningContext
        │
        ├─> IKSolver -> IKResult
        │
        └─> MotionPlanner -> PlannerResult(JointPath)
                                 │
                                 v
                 TrajectoryParameterizer
                                 │
                                 v
                            Trajectory
                                 │
                          SafetyValidator
                                 │
                                 v
                         ExecutionSegment
                                 │
                         TrajectoryExecutor
```


## Important invariants

- `Pose6D` is always XYZ metres + normalized XYZW quaternion + explicit frame ID.
- `JointState`, `JointPath`, `Trajectory`, limits and IK solutions carry explicit ordered joint names.
- Joint order is part of the contract; adapters must not silently reorder vectors.
- `JointPath` is geometric/untimed. `Trajectory` is explicitly time-parameterized.
- Every `Trajectory` starts at `time_from_start_s = 0`.
- Optional trajectory provenance includes limits used, interpolation, scene revision and transform revision.
- `PlanningContext` carries scene and transform revisions so stale plans can be rejected.
- `ExecutionSegment` is bounded by a horizon and records controller period plus scene/transform revisions.
- Planner and IK failures use project-owned machine-readable failure codes.
- VLM/semantic output never bypasses these contracts to command motors directly.

## Failure taxonomy

Current motion failure classes cover:
`invalid_goal`, `transform_stale`, `ik_unreachable`, `collision`,
`optimization_failed`, `timeout`, `dynamic_limit_failed`,
`tracking_error`, `execution_stale`, `backend_unavailable`,
`resource_exhausted`, and `internal_error`.

This list can expand, but adapters must map backend-specific exceptions/status values into a project-owned class.


## Simulator-independent metrics

`telemetry/motion_metrics.py` currently provides:

- joint-space path length in radians;
- trajectory duration;
- peak and RMS finite-difference joint velocity;
- peak and RMS finite-difference joint acceleration;
- peak and RMS finite-difference joint jerk;
- end-effector translation error in metres;
- quaternion angular error in radians;
- replanning splice position/velocity/acceleration discontinuity where enough samples exist.

RMS derivative metrics are currently unweighted over finite-difference samples and all joints.
This definition is deterministic and suitable for Windows tests, but experiment reports must preserve the exact
metric version/definition. W-B/W-E may later propose a scientifically stronger weighting/normalization;
such changes require a versioned metric definition rather than silently changing historical results.

## Limit validator

`safety/joint_limits.py` performs project-owned pre-execution checks for:

- joint position limits;
- finite-difference velocity limits;
- finite-difference acceleration limits;
- finite-difference jerk limits;
- exact joint-order consistency.

Collision and Cartesian workspace checks remain adapter/scene-dependent and are not faked on Windows.


## W-B alignment

The W-B grasp/motion study is compatible with this baseline:
- CuRobo and MPlib can implement `IKSolver` / `MotionPlanner` adapters;
- TOPPRA or another timer can implement `TrajectoryParameterizer`;
- backend objects remain private to adapters;
- scene/transform revision data support stale-plan rejection;
- splice-discontinuity metrics support the proposed receding-horizon gate.

W-B's proposed grasp-candidate expansion is deferred to S1.3 so the motion contract commit does not conflict
with the parallel grasp research output.

## Not yet validated

Windows tests do **not** prove:
- Panthera joint naming/order;
- actual Panthera limits;
- CuRobo or MPlib availability;
- collision-world correctness;
- control-loop frequency;
- tracking accuracy;
- actual jerk after Panthera/RoboTwin execution.

Those remain native-Ubuntu S1.1/S1.2 evidence gates.
