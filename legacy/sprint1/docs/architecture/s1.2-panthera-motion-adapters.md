# S1.2 Panthera Motion Adapter Boundary

## Status

Windows implementation is complete enough for source-audited unit/conformance testing.
Native RoboTwin/CuRobo execution is still pending and must not be inferred from Windows tests.

The direct implementation preserves the project-owned interfaces in
`src/vla_robot_sorting/contracts/interfaces.py` and does not expose CuRobo,
MPlib, SAPIEN, or RoboTwin classes across those boundaries.

## Source-audited RoboTwin behavior

The pinned Panthera/RoboTwin source establishes these facts:

- project `Pose6D` uses quaternion order `xyzw`;
- RoboTwin planner targets use `[x, y, z, qw, qx, qy, qz]`;
- single-arm `Robot.left_plan_path()` plans from the live articulation qpos;
- the single-arm planner object is CuRobo and returns interpolated
  `position` and `velocity` arrays;
- the CuRobo configuration uses `interpolation_dt=1/250`;
- `Robot.set_arm_joints()` writes both drive position and velocity targets;
- each RoboTwin physics step is `1/250 s` by default;
- `Robot.get_left_arm_real_jointState()` is the actual articulation qpos path.

These facts are encoded explicitly rather than inferred from recorded
`joint_action`, which is a drive-target signal.

## Planner adapter

`PantheraRoboTwinMotionPlanner`:

1. requires Panthera joint order `joint1..joint6`;
2. rejects non-world-frame goals;
3. converts `xyzw -> wxyz` explicitly;
4. compares the requested start state with live articulation qpos;
5. rejects stale starts as `EXECUTION_STALE`;
6. maps vendor planner failures/exceptions into project failure codes;
7. returns only project-owned `JointPath` / `PlannerResult` values;
8. retains source-audited 250 Hz velocity/timing data only as compatibility metadata.

The planner does not claim CuRobo support on GTX 1660 Ti until the native
Ubuntu gate runs successfully.

## Timing adapters

Two timing paths intentionally coexist.

### RoboTwin vendor-interpolation bridge

`RoboTwinVendorTrajectoryParameterizer` preserves the exact 250 Hz
position/velocity samples returned by the pinned RoboTwin CuRobo integration.

This exists only to validate the project planner/executor seam without
silently changing the vendor path. It is marked as a compatibility bridge and
does **not** accept ADR-0002 or replace the proposed TOPPRA timing layer.

### Minimum-jerk deterministic fallback

`MinimumJerkStopParameterizer` uses a quintic minimum-jerk profile and
stops at every geometric path knot. Segment duration is derived from velocity,
acceleration, and jerk limits, then rounded to the controller period.

This is deterministic, dependency-free, C2-continuous, and useful for sparse
paths/unit tests. It is intentionally conservative and is not intended to
re-time a dense CuRobo interpolation.

## Joint limits

`load_joint_limits_from_urdf()` reads position and velocity limits from the
exact runtime URDF. Acceleration and jerk are supplied explicitly from the
versioned planner/model configuration because those are not standard URDF
joint-limit fields.

The native planning probe reads Panthera acceleration/jerk from the pinned
`curobo.yml` cspace configuration. No guessed hardware limits are embedded
in the project source.

## Executor adapter

`PantheraRoboTwinTrajectoryExecutor`:

- executes only Panthera `joint1..joint6` trajectories;
- requires the segment controller period to align with trajectory samples;
- checks scene and transform revisions before and during execution;
- cancels stale segments before issuing another command;
- sends position + velocity targets through `Robot.set_arm_joints(..., "left")`;
- advances exactly one RoboTwin physics step per command sample;
- reads actual qpos after the bounded segment;
- converts excessive tracking error into failed/replan-required feedback.

The executor does not yet command the gripper. Gripper closure belongs to the
later grasp/execution integration and must remain separate from arm motion
until the S1.3 grasp contract is frozen.

## Native probe

`scripts/linux/probe_panthera_project_motion.py` is a non-actuating planning
probe. It creates small translation and orientation goals from the current
Panthera end-effector pose, routes them through the project planner adapter,
loads exact runtime joint limits, converts the vendor interpolation to a
project trajectory, and runs joint-limit validation.

It does **not** move the robot. A later native execution gate should be enabled
only after S1.1 simulator bring-up passes and this planning/timing evidence is
reviewed.


## MPlib fallback adapter

`PantheraRoboTwinMPlibPlanner` is implemented as a source-audited fallback
candidate. It explicitly calls RoboTwin's MPlib `plan_pose` RRT path instead
of inheriting Panthera's current `mplib_screw` config, because the source
documents screw interpolation as non-avoidance planning that only succeeds
when the interpolated path is already collision-free.

The adapter:
- uses the same world-frame project goal conversion;
- rejects stale start states against live articulation qpos;
- applies RoboTwin's gripper-to-end-link transform;
- extracts only `joint1..joint6` if MPlib returns full active-joint vectors;
- preserves 250 Hz position/velocity samples behind the same compatibility
  timing bridge.

This is still **pending native B3 validation** and is not promoted above CuRobo.


## Bounded motion cycle

`BoundedMotionController` now composes the stable S1.2 interfaces for one
revision-locked cycle:

1. plan;
2. validate geometric path;
3. parameterize;
4. validate timed trajectory;
5. build an aligned bounded segment;
6. execute once.

It deliberately does not loop or recover. S1.5 will own repeated
re-observe/replan/recover behavior and can invoke this bounded primitive.

`build_execution_segment()` snaps a requested horizon to the previous
trajectory waypoint, carries the predicted stop state, and rejects stale
trajectory revisions before execution.


## Concrete joint-limit safety

`JointLimitSafetyValidator` checks:

- path and trajectory joint order;
- path position bounds;
- trajectory position, velocity, acceleration, and jerk via finite differences;
- scene revision consistency;
- transform revision consistency;
- accidental use of a different `JointLimits` set at trajectory validation.

Collision validity is still owned by the planner/backend in this stage.
A future scene-aware collision validator can be composed behind the same
`SafetyValidator` interface without changing the controller.
